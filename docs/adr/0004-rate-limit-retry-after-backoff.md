# MediaWiki HTTP 429s are retried by honoring `Retry-After` in the transport

During generation of the visual-language prototype's real crawl feeds, the Crawler failed repeatedly with `MediaWiki API returned HTTP 429`. Two crawl runs launched concurrently (each with the Crawler's 4 concurrent requests, ~2 API calls per page) died within minutes; a single run was also throttled without retry logic. The fix that worked, proven end-to-end on two real runs (2000 and 3000 nodes): a throwaway httpx transport wrapper that, on HTTP 429, sleeps `min(Retry-After, 45)s` and retries the same request, up to 10 attempts. With backoff active, both deep runs completed without a single failure, keeping the Crawler's own code untouched.

**Decision**: rate limiting is handled at the *transport layer*, not in crawl logic: when any HTTP client of wikiGraph hits 429, it waits the server-advertised `Retry-After` (capped to a sane ceiling) and retries the identical request silently, surfacing an error only after exhausting its budget. One layer honors it for all callers — concurrent runs, the API UI, future batch tools — instead of each crawl loop reinventing politeness. By default, crawl runs should also not be launched concurrently.

**Why transport-level**: the retry is transparent to the Crawler (it sees plain successes), which keeps crawl semantics pure (breadth-first, cap, referential integrity) and makes the policy swappable in one place. `Retry-After` from Wikipedia is trustworthy (observed 11 s / 17 s / 28 s / 32 s windows); blind exponential backoff would both disrespect the server's guidance and thrash under load. Fail-loud after exhausting retries preserves honesty for the user in the UI (the launch surface already shows the error inline).

**Considered Options**: fail-fast without retry (rejected: any real crawl burst fails, as observed); client-side crawl-loop retries around each API call (rejected: splatters politeness logic across every caller, and the probe/UI layers would each need it); fixed sleep-before-each-request (rejected: penalizes healthy traffic and cannot adapt to advertised windows).

**Scope note**: crawl-cap and crawl-performance work is a separate future effort, but this ADR is the banked pattern: when that work opens, the backoff transport becomes part of the Crawler's default stack (`create_app` / `Crawler` already accept a custom httpx transport — the seam exists).
